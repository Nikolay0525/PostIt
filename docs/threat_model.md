## System Overview

Коротко опишіть систему та її основні елементи, достатньо для розуміння моделі загроз.

**DFD (Data Flow Diagram, діаграма потоків даних)** - модель, що показує, як дані переміщуються через систему, де вони обробляються, де зберігаються та з якими зовнішніми суб'єктами система взаємодіє. У контексті STRIDE DFD використовується як основа аналізу загроз.

У цьому документі використовуються такі типи елементів DFD:

- **External Interactor** - зовнішній користувач або система;
- **Process** - компонент, що виконує обробку;
- **Data Store** - сховище даних;
- **Data Flow** - передавання даних між елементами;
- **Trust Boundary** - межа між областями з різним рівнем довіри.

У прикладах нижче тип елемента завжди вказується окремо від його конкретної назви.

**Приклад елементів системи:**

| ID | DFD Type | Name |
| --- | --- | --- |
| E1 | External Interactor | User |
| E2 | External Interactor | Mail Service |
| P1 | Process | Client |
| P2 | Process | Web API |
| D1 | Data Store | Database |
| F1 | Data Flow | Client -> Web API |
| F2 | Data Flow | Web API -> Database |
| F3 | Data Flow | Web API -> Mail Service |
| TB1 | Trust Boundary | Client / Web API |

**Приклад зв'язків:**

- `E1 User` взаємодіє з `P1 Client`.
- `P1 Client` передає дані до `P2 Web API` через `F1 Client -> Web API`.
- `F1 Client -> Web API` перетинає `TB1 Client / Web API`.
- `P2 Web API` передає дані до `D1 Database` через `F2 Web API -> Database`.
- `P2 Web API` передає дані до `E2 Mail Service` через `F3 Web API -> Mail Service`.

## STRIDE Analysis

Канонічна відповідність STRIDE типам елементів DFD:

| DFD Element | S | T | R | I | D | E |
| --- | :---: | :---: | :---: | :---: | :---: | :---: |
| External Interactor | ✓ |  | ✓ |  |  |  |
| Data Flow |  | ✓ |  | ✓ | ✓ |  |
| Data Store |  | ✓ |  | ✓ | ✓ |  |
| Process | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

Позначення: **S** - Spoofing; **T** - Tampering; **R** - Repudiation; **I** - Information Disclosure; **D** - Denial of Service; **E** - Elevation of Privilege.

Для кожного елемента системи заповнюються лише релевантні категорії.

| Element | S | T | R | I | D | E |
| --- | --- | --- | --- | --- | --- | --- |
| **E1 User** *(External Interactor)* | Зловмисник може діяти від імені легітимного користувача, використавши викрадені облікові дані. | - | Користувач може заперечувати виконання критичної операції за відсутності достатнього підтвердження її виконання. | - | - | - |
| **F1 Client -> Web API** *(Data Flow)* | - | Запит може бути змінений до його обробки сервером. | - | Дані запиту або відповіді можуть бути перехоплені. | Потік може бути заблокований або перевантажений. | - |
| **D1 Database** *(Data Store)* | - | Дані можуть бути несанкціоновано змінені або видалені. | - | Несанкціонований доступ може призвести до розкриття даних. | Блокування або перевантаження сховища може зробити дані недоступними. | - |
| **P2 Web API** *(Process)* | Порушник може виконувати запити від імені іншого користувача. | Вхідні дані або внутрішній стан можуть бути несанкціоновано змінені. | За відсутності достатнього аудиту критичну операцію неможливо однозначно пов'язати з конкретним суб'єктом. | API може повернути дані, до яких суб'єкт не повинен мати доступу. | Велика кількість запитів може виснажити ресурси API. | Помилка авторизації може дозволити звичайному користувачу виконати привілейовану операцію. |

> Якщо одна й та сама проблема породжує кілька різних STRIDE-загроз, вони фіксуються у відповідних клітинках. STRIDE-категорії не є взаємовиключними.
